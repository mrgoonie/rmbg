# Fix CI Lockfile Issue - pnpm-lock.yaml Out of Sync

**Date:** 2025-10-01
**Status:** Ready for Implementation
**Priority:** High - Blocking CI/CD Pipeline

---

## Overview

The GitHub Actions CI pipeline is failing during the `Install dependencies` step because the `pnpm-lock.yaml` file is out of sync with the newly added `packages/node/package.json`. The lockfile was not updated when the Node.js SDK package was committed to the repository.

---

## Problem Analysis

### Root Cause

The commit `b4e26ef feat(node): add Node.js SDK package with comprehensive tests` added a new package at `packages/node/` with dependencies, but the `pnpm-lock.yaml` was not updated to include this package's dependency tree.

### Error Details

**GitHub Actions Run:** https://github.com/mrgoonie/rmbg/actions/runs/18156332093/job/51676939460

**Error Message:**
```
ERR_PNPM_OUTDATED_LOCKFILE  Cannot install with "frozen-lockfile" because pnpm-lock.yaml is not up to date with <ROOT>/packages/node/package.json

Note that in CI environments this setting is true by default. If you still need to run install in such cases, use "pnpm install --no-frozen-lockfile"

Failure reason:
specifiers in the lockfile ({}) don't match specs in package.json ({"@types/node":"^20.10.0","rimraf":"^5.0.1","tsup":"^8.0.0","typescript":"^5.2.2","vitest":"^1.0.0","onnxruntime-node":"^1.16.2","sharp":"^0.33.0"})
```

**Key Facts:**
- The lockfile shows `specifiers in the lockfile ({})` - meaning `packages/node` is completely missing from the lockfile
- The package was added in commit `b4e26ef` but lockfile was not regenerated
- CI uses `pnpm install --frozen-lockfile` which requires an exact match between package.json and lockfile
- The current commit on main is `bed64c0` which has the docs but still missing lockfile update

## Solution Design

### Approach

Update the `pnpm-lock.yaml` by running `pnpm install` locally to regenerate the lockfile with the new `packages/node` package included.

### Why This Solution

1. **Correct Fix:** The lockfile must reflect all workspace packages and their dependencies
2. **CI Requirement:** The `--frozen-lockfile` flag in CI requires exact match
3. **Best Practice:** Lockfiles should always be committed with package.json changes
4. **Monorepo Pattern:** pnpm workspaces require all packages to be registered in the lockfile

## Performance Considerations

### CI Cache Impact

**Cache Key:**
```yaml
key: ${{ runner.os }}-pnpm-store-${{ hashFiles('**/pnpm-lock.yaml') }}
```

**Impact:**
- The lockfile hash will change
- This will invalidate the existing CI cache
- First build after the fix will be slower (needs to rebuild cache)
- Subsequent builds will use the new cache and be fast again

**Mitigation:**
- This is expected and normal behavior
- No action needed - cache will regenerate automatically
- Future builds will benefit from the updated cache

## Risks & Mitigations

### Risk 1: Local vs CI Dependency Mismatch

**Risk:** Different pnpm or Node versions might resolve dependencies differently

**Likelihood:** Low

**Mitigation:**
- Use same Node version (20.x) as CI
- Use same pnpm version (9.x) as CI
- The workflow already specifies exact versions

### Risk 2: Native Dependencies Build Issues

**Risk:** `sharp` and `onnxruntime-node` have native bindings that might fail on CI

**Likelihood:** Low

**Impact:** Build step might fail

**Mitigation:**
- Both packages have prebuilt binaries for common platforms
- Ubuntu 24.04 (CI environment) is well-supported
- If issues occur, we can add platform-specific build steps

### Risk 3: Cache Poisoning

**Risk:** Old cache might cause issues after lockfile update

**Likelihood:** Very Low

**Impact:** CI might use wrong dependencies

**Mitigation:**
- Cache key includes lockfile hash, so it will automatically invalidate
- GitHub Actions cache is versioned and isolated per key
- No manual cache clearing needed

### Troubleshooting

**If `pnpm install` fails:**

- Check pnpm version: `pnpm --version` (should be 9+)
- Clear pnpm cache: `pnpm store prune`
- Try again: `rm -rf node_modules && pnpm install`

**If CI still fails after fix:**
- Check lockfile was actually committed: `git log --oneline -1`
- Check lockfile content: `grep "packages/node" pnpm-lock.yaml`
- Check CI logs for different error messages
- Consider cache issues (wait for cache to regenerate)
